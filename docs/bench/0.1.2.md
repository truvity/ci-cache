# 0.1.2 — 2026-09-24

The first baseline. It exists so the streaming and concurrency work has
something to move, and so a later claim of "faster" can be checked.

## How it was taken

| | |
|---|---|
| server | one replica, `0.1.2`, `server.concurrency=256`, no CPU or memory limits set |
| server node | `m6a.large` — 2 vCPU, 8 GiB |
| disk tier | gp3, default throughput |
| object store | S3 Standard, same region |
| load generator | a pod on a separate `m6a.large`, in the cluster, over the service DNS |
| corpus | 1000 lookups / 2000 objects / 756 MB, seed 1 |

Driven in-cluster, not over a port-forward. A port-forwarded run measures the
operator's link to the cluster and plateaus long before the server does; the
same sweep from a laptop peaked at 90 MB/s and got *slower* as concurrency
rose.

## What the numbers say

**Throughput plateaus near 300 MB/s and the transport does not change that.**
h2c peaks at 324 MB/s, http1 at 297. Both sit in the same band, so the single
multiplexed connection is *not* the ceiling it was suspected of being. Whatever
the limit is, it is not the choice of transport.

**The plateau is real, not a burst.** Four consecutive 60-second points at
concurrency 64 gave 295.0, 297.2, 295.3 and 296.4 MB/s — flat across four
minutes. There is no credit being spent that would run out under a longer CI
load.

**The server is not CPU-bound at that rate, but it is not far off.** Under
concurrency 64 it used 1257m of the node's 2000m — about 63% of a 2-vCPU
instance it does not have to itself, since it runs with no requests or limits
set. Roughly doubling throughput would make CPU the constraint on this node.

**Concurrency 1024 is not a working operating point today.** h2c produced
40225 errors and *lower* throughput than 256; http1 produced 992. Past the
plateau, added concurrency buys queueing and failures rather than bytes.

**First byte degrades faster than throughput.** From concurrency 1 to 256 the
p50 wait for the first byte goes 1.4 ms → 114 ms, an 80× rise, while
throughput rises 2.8×. Requests are queueing, not streaming.

## Not covered

`cold-bucket` and `mixed` are absent, and the reason is a property of the
deployment rather than the bench: the admin port has no ingress allowance from
any pod, so nothing running in the cluster can put the server into a
cold-disk state. Measuring the fault-in path in-cluster needs either a
benchmark-dedicated deployment or a deliberate path to the admin port. Taking
those numbers over a port-forward instead would measure the operator's link,
which is how this file would end up comparing two different things.
